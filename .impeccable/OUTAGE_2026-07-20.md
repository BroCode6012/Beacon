# Signal edge discovery outage — cause, established before any change

**Window:** 2026-07-20 16:58:46 UTC → 2026-08-06 21:15 UTC (17 days).

## Verdict: it HUNG. It did not exit.

`signal-edge.service` was `active (running)` the whole time, **Main PID 330968 —
the same PID named in the frozen status file** — with 25 tasks, RSS ~970 MB and
22d07h elapsed. Because the process never exited, `Restart=on-failure` never had
anything to act on. That is the whole reason 17 days passed silently.

## Evidence

| Check | Result | Rules out |
|---|---|---|
| `ps` on 330968 | alive, `Ssl`, 25 threads, 16h48m CPU total | clean exit / crash |
| all 25 thread states | every one `S` (sleeping), kernel stack `futex_wait` | busy loop / spin |
| `ss -tanp` for the PID | **10 stale HTTPS sockets to Google**: 5 `ESTAB` idle, **5 `CLOSE-WAIT` with recv-q=1** | network is fine, app is stuck |
| `df -h` | 16% used, 38 G free | disk full |
| `free -m` | 9.7 G available, no swap | OOM |
| `uptime` | up 25 days (boot 2026-07-12) | reboot |
| `journalctl -u signal-edge --since "2026-07-20 16:00"` | **no entries at all** | crash trace / unhandled exception |
| jobs dir | 41 plans present, run already past parse into "collecting" | unparseable plan |
| status file | `status: running`, zero errors ever recorded | expired key / quota |

`CLOSE-WAIT` is the decisive one: the peer sent FIN and our side never called
`close()`. Those threads were parked inside a socket read that will never return.

## Mechanism (confirmed in source)

1. `collector._free_outcomes` fans 125 queries over 24 threads and waits with
   `as_completed(futures)` then `future.result()` — **neither has a timeout**.
2. Each task calls `ScrapetubeProvider.search` → `scrapetube.get_search` →
   `requests.Session.get/post` — the vendored library passes **no `timeout=`**.
   `requests` with no timeout blocks on the socket forever.
3. On 20 July several of those connections stalled mid-read. No exception was
   raised, so `_search_free`'s retry logic (which only catches exceptions) never
   engaged.
4. The main thread blocked in `as_completed`, and `ThreadPoolExecutor.__exit__`
   would have blocked in `shutdown(wait=True)` anyway. Deadlock, permanently.
5. The status file is only rewritten between steps, so it froze mid-run on
   `run-00002280` / "collecting 125 queries".
6. Systemd saw a live process. Nothing failed. Nothing alerted.

The organizer (PID 330973) was never broken — it is still updating its status
today. It reported `waiting / queued_jobs: 0` simply because discovery had
stopped feeding it. Its 269 "successful, 0 channels" cycles are the same
silence, seen from the laptop.

## Therefore the two required fixes

- **Stall must become a failure.** A hang produces no exit code, so systemd is
  blind. Something must convert "no progress for N minutes" into a restart.
- **The laptop must not read silence as success.** A stale `updated_at` and a
  run of zero-channel cycles must surface as an error, not 269 green ticks.
